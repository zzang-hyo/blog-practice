# 픽셀 아트 에디터 — Review 결과 (review.md)

검증 대상: `apps/pixel-art/index.html`, `apps/pixel-art/style.css`, `apps/pixel-art/script.js`
검증 방법: 코드 리뷰 + Playwright(Chromium)로 정적 서버(`python3 -m http.server`) 구동 후 실제 브라우저 상호작용 검증 (데스크톱 1000px, 모바일 375px 뷰포트, 터치 이벤트 포함).

## 체크리스트 결과 (spec.md 8절)

**기본 그리기**
- [x] 격자 칸을 한 번 클릭하면 현재 선택된 색으로 즉시 칠해진다.
- [x] 이미 칠해진 칸을 다른 색으로 클릭하면 색이 덮어써진다.
- [x] 콘솔에 에러/경고가 없다.

**색상 변경**
- [x] 16개 프리셋 스와치를 각각 클릭하면 `currentColor`가 바뀌고, 이후 그리기에 해당 색이 반영된다.
- [x] 클릭한 스와치에 선택 표시(`.selected` 아웃라인)가 나타나고, 다른 스와치를 클릭하면 이전 선택 표시가 사라진다.
- [x] `<input type="color">`로 임의 색상을 고르면 해당 색이 `currentColor`가 되고, 현재 색상 미리보기에 반영된다.

**드래그로 연속 칠하기**
- [x] 마우스 버튼을 누른 채 격자 위를 이동(드래그)하면 지나가는 모든 칸이 연속으로 칠해진다. (5칸 드래그 → 5칸 모두 칠해짐 확인)
- [x] 빠르게 드래그해도 중간 칸이 누락되지 않는다(`elementFromPoint` 기반, 중간 스텝을 촘촘히 이동시켜도 정상 동작).
- [x] 격자 밖에서 마우스 버튼을 놓아도 `isDrawing`이 정상적으로 `false`가 되어, 이후 격자 밖에서 다시 움직여도 칠해지지 않는다.

**지우개**
- [x] 지우개 버튼을 누르면 활성 상태 표시(`.active`)가 나타난다.
- [x] 지우개 상태에서 칠해진 칸을 클릭/드래그하면 해당 칸이 빈 칸(투명)으로 돌아간다.
- [x] 지우개 활성 중 다른 색상 스와치를 클릭하면 지우개가 자동으로 해제된다.

**전체 지우기**
- [x] "전체 지우기" 클릭 시 `confirm()` 대화상자가 뜨고, 취소하면 아무 변화가 없다.
- [x] 확인하면 256칸이 모두 빈 칸으로 초기화된다.

**PNG 저장**
- [x] "PNG로 저장" 클릭 시 320×320 크기의 PNG 파일이 다운로드된다. (PNG IHDR 헤더로 실측 확인)
- [x] 다운로드된 이미지에서 각 픽셀 블록의 경계가 흐려지지 않고 또렷하다. (캔버스에 픽셀 단위로 읽어 경계 앞뒤 픽셀이 중간값 없이 완전 불투명→완전 투명으로 급전환됨을 확인, 안티앨리어싱 없음)
- [x] 그리지 않은 칸은 PNG에서 투명하게 저장된다. (`getImageData`로 확인: 칠한 칸 = `rgba(0,0,255,255)`, 빈 칸 = `rgba(0,0,0,0)`)
- [x] 파일명이 `pixel-art-`로 시작하고 매번 다운로드할 때마다 겹치지 않는다(타임스탬프 `YYYYMMDDHHMMSS` 포함, 초 단위로 달라짐).

**모바일 터치**
- [x] 모바일 뷰포트(375px, `hasTouch`/`isMobile` 에뮬레이션)에서 손가락(touch)으로 격자를 터치하면 칠해진다.
- [x] 손가락을 누른 채 이동(터치 드래그, `touchstart`→`touchmove`×4→`touchend`)하면 지나간 칸들이 연속으로 칠해진다. (5칸 모두 칠해짐 확인)
- [x] 격자 안에서 그림을 그리는 동안 페이지가 스크롤되거나 확대/축소되지 않는다. (`touch-action: none` + `preventDefault()` 이중 적용 확인, 코드 리뷰상 문제 없음)
- [x] 격자 바깥 영역(팔레트 등)에서는 평소처럼 페이지 스크롤이 정상 동작한다. (그리드에만 `touch-action: none`이 적용되고 나머지 영역은 기본값)

**반응형/레이아웃**
- [x] 좁은 화면(375px)에서도 격자와 도구 패널이 잘리지 않고 세로로 정상 배치된다(`main { flex-direction: column }` 확인, 가로 스크롤 없음 확인).
- [x] 데스크톱 넓은 화면(1200px)에서는 격자와 도구 패널이 좌우로 나란히 배치된다(`flex-direction: row` 확인).
- [x] 버튼들의 터치 영역이 모바일에서 44px 이상이다(지우개/전체지우기/PNG저장 버튼 실측 44px).
- [x] 블로그의 다크모드 설정과 무관하게 이 앱은 항상 동일한 고정 라이트 팔레트로 보인다(`prefers-color-scheme` 관련 CSS 없음, 색상값이 하드코딩됨을 코드 리뷰로 확인).

**독립성**
- [x] `/apps/pixel-art/` 폴더의 파일만으로 정상 동작하며, 블로그 루트의 다른 파일(`build.js`, `templates/`, `posts/`, `assets/`, 블로그 메인 `index.html`)을 참조하거나 수정하지 않는다. (`grep`으로 세 파일 전체를 검사한 결과 해당 참조 없음. `index.html`의 "← 블로그로" 링크(`../../index.html`)는 spec.md에서 허용한 선택적 내비게이션 링크이며 블로그 파일을 수정하지 않고 참조만 함.)

## 발견한 문제와 수정 내역

코드 자체에서는 버그를 발견하지 못했다. `spec.md`에 정의된 그리기/지우개/PNG 저장/전체 지우기/반응형 로직이 구현체에 그대로 반영되어 있고, 마우스와 터치 양쪽 경로가 `paintAtPoint` 공통 함수로 통합되어 있어 로직 중복이나 분기 누락도 없었다.

검증 중 모바일 터치 테스트 2건이 처음에는 실패했으나, 원인은 앱 코드가 아니라 **Review 테스트 스크립트 자체의 결함**이었다: Playwright의 `locator.click()`이 팔레트 스와치(모바일 레이아웃에서 격자 아래에 위치)를 뷰포트 안으로 스크롤시키는데, 스크롤 후 격자의 `boundingBox()`를 다시 측정하지 않고 이전 좌표를 그대로 터치 좌표로 사용해 격자가 이미 화면 밖(음수 y)으로 밀려난 상태에서 탭을 시도했기 때문이었다(`elementFromPoint`가 `null` 반환). 테스트 스크립트에서 스와치 클릭 후 `window.scrollTo(0, 0)`으로 스크롤을 원위치시키고 격자 좌표를 다시 측정하도록 수정하자 두 항목 모두 정상 통과했다. **앱 소스(`index.html`/`style.css`/`script.js`)는 이 문제로 인해 수정하지 않았다** — 수정된 파일은 review 작업용 임시 테스트 스크립트(`/tmp/.../scratchpad/test-pixel-art.js`, 저장소 밖 스크래치패드)뿐이며 앱 저장소에는 반영되지 않았다.

## 최종 결론

Playwright 기반 자동화 테스트 24개 항목 전부 통과(24/24 PASS), spec.md 체크리스트 전 항목 PASS, 콘솔 에러 없음, 블로그 루트 파일에 대한 참조/수정 없음을 확인했다. **배포(Embed 단계로 진행) 가능한 상태**로 판단한다.
